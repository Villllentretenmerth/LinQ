# Журнал событий и дашборд (team_94)

Сервис хранит каждое подтверждённое нарушение с временными метками, кадром-доказательством
и отметкой о реакции ответственного. Из него же берут данные все уровни дашборда.

**Стек:** FastAPI + PostgreSQL 16 (SQLAlchemy 2). Для локальной разработки без Docker работает и на SQLite.

## Запуск

```bash
cd journal
docker compose up -d --build                        # PostgreSQL + API на http://localhost:8000
docker compose exec api python -m scripts.seed_demo --reset --patterns /patterns   # демо-данные за 30 дней
```

Дашборд: **http://localhost:8000/** (откроется `/ui/`) · документация API: http://localhost:8000/docs

Без Docker (SQLite в файле `journal.db`):
```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
python -m scripts.seed_demo --reset
```

Тесты (11 штук, проходят на SQLite и PostgreSQL 16):
```bash
python -m pytest -q                                                   # временная SQLite
TEST_DATABASE_URL=postgresql+psycopg://journal:journal@localhost:5432/journal_test python -m pytest -q
```
Тесты пересоздают таблицы, поэтому для PostgreSQL указывайте **отдельную** тестовую базу.

## Дашборд (папка `web/`)

Обычный HTML + JS без сборки, графики — ECharts (лежит в `web/vendor`, интернет не нужен).
Отдаётся тем же сервисом по адресу `/ui/`. Светлая и тёмная тема — по настройке системы.

| Вкладка | Уровень и роль | Что есть |
|---|---|---|
| **Оператор** | 1 — оператор / диспетчер; 2 — мастер (выбирает свой участок, выбор запоминается) | живая лента через WebSocket, критичные сверху; красная плашка и звук на критичное событие; карточка события; кнопки «Подтвердить / Передать мастеру / Ложное срабатывание / Закрыть» с комментарием и историей |
| **Журнал** | 3 — охрана труда, юристы | фильтры по периоду, участку, камере, нарушению, категории, уровню, статусу; постраничный вывод; карточка с историей реакций; выгрузка CSV по тем же фильтрам |
| **Аналитика** | 4 — руководство | период 7 / 30 / 90 дней и участок; итоги (всего, критичных, precision, время до тревоги, доля ночной смены); нарушения по дням, топ нарушений, участки по сменам, «участок × час суток»; у каждого графика есть табличный вид |
| **Система** | 5 — ИТ | узлы LinQ: загрузка TPU, FPS по потокам, задержки каждой модели, сколько ещё камер выдержит узел; графики загрузки и FPS за час (обновление каждые 5 с); задержка конвейера, время до тревоги и precision по правилам |

**Для показа на защите:** кнопка «Тестовое событие» в шапке создаёт правдоподобное событие
(`POST /api/dev/simulate`), и оно сразу появляется в ленте оператора, а критичное — с плашкой и звуком.
Кнопка видна при `DEMO_MODE=1` (по умолчанию); на реальном стенде поставьте `DEMO_MODE=0`.

## Метрики узлов LinQ (загрузка TPU и FPS)

Каждый узел присылает **окна метрик**: сколько кадров обработано по каждому потоку, сколько времени
TPU был занят каждой моделью, сколько кадров выброшено, загрузка CPU.

**Как считается загрузка TPU.** По нашим замерам: время, когда TPU был занят инференсом, делённое
на длину окна (busy / wall). Если API LinQ отдаёт собственную загрузку ускорителя, передайте её
(`MetricsReporter.set_native_util()` или поле `tpu_util`), она важнее расчётной.

**Сколько камер выдержит узел.** Цена кадра = время TPU на кадр со всем каскадом моделей
(`tpu_busy_ms / frames`). Максимум потоков = `предел загрузки × 1000 × ядер TPU / (цена кадра × FPS на камеру)`.
Целевой FPS и предел загрузки выбираются на вкладке «Система».

Откуда берутся метрики:

| Источник | Что запускать | `source` |
|---|---|---|
| Конвейер на узле | `client/metrics_client.py` — `with rep.timer("yolo-pose"): ...`, `rep.frame("cam-01")`, окно раз в 5 с | `pipeline` |
| Замер в Jupyter хакатона | `../bench/linq_bench.py` → `bench_result.json` → `python -m scripts.import_metrics bench_result.json --url http://localhost:8000` | `bench` |
| Демо для показа | `scripts/seed_demo.py` (2 узла, история за 2 часа) + живое обновление каждые 5 с при `DEMO_MODE=1` | `demo` |

Демо-узлы помечены в интерфейсе плашкой «демо», а над карточками висит пояснение — чтобы их не приняли за замеры.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/metrics` | окно метрик узла |
| GET | `/api/metrics/nodes?target_fps=10&util_cap=0.8` | узлы: последние метрики, в сети ли, запас по камерам |
| GET | `/api/metrics/series?minutes=60` | история загрузки TPU и FPS для графиков |

## Как событие попадает в журнал

```
движок: кандидат → подтверждение N из M → POST /api/events  (event_uid = ключ идемпотентности)
                                         → POST /api/events/{id}/media   (кадр, клип)
        трек ушёл / нарушение закончилось → POST /api/events/{id}/end
оператор: «подтверждено / ложное / мастеру» → POST /api/events/{id}/status  (+ запись в историю)
интерфейс: живая лента ← WebSocket /ws/events
```

Из движка удобнее всего через `client/journal_client.py`.

## Временные метки события

| Поле | Что это | Зачем |
|---|---|---|
| `started_at` | первый кадр-кандидат | начало нарушения |
| `confirmed_at` | нарушение подтверждено, ушла тревога | **время до тревоги** = `confirmed_at − started_at` |
| `frame_ts` | время кадра, на котором подтвердили | **задержка конвейера** = `received_at − frame_ts` |
| `received_at` | время записи в журнал (сервер) | |
| `ended_at` | нарушение закончилось | длительность |
| `reviewed_at` | реакция оператора или мастера | время реакции человека |

Все метки хранятся в UTC. Смены, графики и выгрузка считаются в часовом поясе предприятия
(`PLANT_TZ`, по умолчанию `Europe/Moscow`; в запросах можно передать `tz=`).

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/events` | создать событие (идемпотентно по `event_uid`) |
| POST | `/api/events/{id}/media?kind=snapshot\|clip` | приложить кадр или клип |
| POST | `/api/events/{id}/end` | закрыть событие |
| POST | `/api/events/{id}/status` | статус от оператора: `confirmed`, `false_alarm`, `sent_to_master`, `resolved` |
| GET | `/api/events` | журнал с фильтрами и пагинацией |
| GET | `/api/events/{id}` | карточка события с историей реакций |
| GET | `/api/events/export.csv` | выгрузка для проверяющих (Excel открывает кириллицу) |
| GET | `/api/stats/summary` | итоги: по паттернам, камерам, участкам, статусам, сменам |
| GET | `/api/stats/timeseries?bucket=hour\|day` | динамика с разбивкой по паттернам |
| GET | `/api/stats/heatmap?rows=area\|camera\|pattern` | матрица «участок × час суток» |
| GET | `/api/stats/quality` | precision по отметкам оператора, время до тревоги и задержка (p50, p95) |
| GET/PUT | `/api/cameras` | камеры и участки |
| WS | `/ws/events` | живая лента: `event_created`, `event_updated`, `event_ended` |

**Фильтры** для журнала, статистики и выгрузки одинаковые:
`pattern_id` (можно несколько), `category`, `severity`, `camera_id` (несколько), `area` (несколько),
`zone`, `status` (несколько), `date_from`, `date_to`.

## Какой уровень дашборда что берёт

| Уровень | Запросы |
|---|---|
| 1. Оператор | WebSocket-лента, `GET /api/events?status=new`, `POST …/status` |
| 2. Мастер | `GET /api/events?area=…&date_from=<начало смены>` |
| 3. Охрана труда, юристы | журнал с фильтрами, карточка с историей, `export.csv` |
| 4. Руководство | `summary` (участки × смены), `timeseries`, `heatmap` |
| 5. ИТ | `quality` (precision по правилам, задержки), `/health` |

## Демо-данные

`scripts/seed_demo.py` создаёт ~1700 событий за 30 дней по 8 камерам и 5 участкам. Паттерны
берутся из YAML-карточек в `../patterns`. В данные заложен сквозной пример из кейса:
- склад отгрузки даёт около 40% нарушений, больше всего в ночную смену;
- пики приходятся на первые часы смены (08–09 и 20–21);
- в последние 10 дней, после «инструктажа», нарушений на складе заметно меньше.

Все демо-события помечены `extra.demo = true`.

## Видеопримеры при первом открытии

В демо-режиме (`DEMO_MODE=1`, `DEMO_SEED=1`, по умолчанию) сервер добавляет
20 разных учебных записей: 10 падений UR Fall и 10 записей бега KTH. Каждая содержит
видеоклип H.264 и кадр-превью, источник и условия использования. Медиа включены в
`web/dataset-media` и доступны без скачивания при запуске, в том числе в Docker.

Это разметка датасетов, не результат детектора. Бег сам по себе не доказывает
нарушение требований безопасности. Материалы предназначены для некоммерческого
использования; авторы, лицензии и изменения указаны в `web/dataset-media/ATTRIBUTION.md`.

Повторный запуск не создаёт дубликаты и сохраняет решения оператора. Старые пустые
автоматические демо-карточки удаляются только если они не проверены и не имеют видео;
реальные события и история проверки сохраняются. Рабочие тревоги могут появляться
до готовности видео, как и раньше. Чтобы видеть все примеры, выберите все участки.
`DEMO_SEED=0` отключает автоматическое добавление; `DEMO_MODE=0` отключает демо-режим.
Ранее сохранённые видеопримеры эти переключатели не удаляют.

## Звук

Короткое «ку-ку» (около 0,55 секунды) звучит при новом событии выбранного участка
и после успешного сохранения решения оператора. При ошибке отправки подтверждающего
звука нет. Кнопка «Звук» отключает оба сигнала; при включении проигрывает образец.
Для разрешения звука браузеру требуется первое нажатие или действие клавиатурой
на странице. Звук синтезируется локально, внешние аудиофайлы не нужны.
