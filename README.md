## Результаты к чек-поинту 3

**Качество** на 18 роликах команды (10 нарушений + 8 ловушек), `eval/quality_after.md`: найдено 10 из 10,
ложных тревог 0, тревог на ловушках 0, одно оповещение на нарушение, время до тревоги — медиана 2,2 с.

**Модель поведения `behavior_v1_open`** обучена только на открытых данных (NTU60, HMDB51, KTH) и роликов команды
не видела: на отложенной части наборов падение — recall 99% / precision 97%, бег — 94% / 82%. На 18 роликах команды
с моделью для бега (по умолчанию в `core/cameras.yaml`) — 10 из 10, 2 ложные тревоги; с моделью для бега и падения —
9 из 10, 3 ложные (`core/models/behavior_v1_open.report.md`).
⚠️ Пороги подобраны на этих же роликах — это не оценка на новых данных.

**Скорость на LinQ TPU** (облако хакатона, свои программы `.tpu`, int8, O5):

| Модель | Как часто | TPU p50 | TPU среднее | p95 |
|---|---|---|---|---|
| yolo-pose | каждый кадр | 8,6 мс | 14,0 мс | 43,7 мс |
| yolo-det | каждый 3-й кадр | 13,1 мс | 17,5 мс | 50,4 мс |
| **каскад** | | | **19,8 мс/кадр** | |

Узел держит ≈ 50 кадров/с: **8 камер при 5 FPS или 4 при 10 FPS** (загрузка TPU ≤ 80%). На стенде полный
круг 210–240 мс — это пересылка ~9 МБ кадра по сети, на площадке её нет.

## Ключевые решения (чтобы говорить одно и то же)

- **5 категорий нарушений** по тому, какой сигнал видит система: среда, поведение во времени, зона,
  взаимодействие, экипировка. Любое нарушение — одна категория или комбинация (`patterns/README.md`).
- **Новое нарушение = карточка YAML**, конвейер не меняется. Цена — только настройка (зоны)
  или новый класс в одной из общих моделей.
- **Всего 4 модели на инференсе, общие для всех карточек**: `yolo-pose` (люди + скелет), `yolo-det`
  (техника, груз, огонь, дым), `behavior_v1` (1D-CNN по окну скелета трека, многоклассовая),
  `crop_attr_v1` (одна многоголовая сеть по вырезкам: каска, жилет, перчатки, привязь, телефон, сигарета).
  Никаких «миллиона бинарных классификаторов».
- **Каскад:** на каждом кадре — только лёгкие модели; вырезки классифицируются только для кандидатов,
  с кэшем по треку.
- **Поведение — во времени:** ByteTrack (фильтр Калмана внутри) даёт ID и историю; окно 1–2 с.
- **Двухэтапное подтверждение:** высокий порог открывает кандидата, низкий — продлевает;
  N из M окон; одно событие на трек + блокировка повторов по «камера + зона + тип».
- **RTSP:** читатель «только последний кадр» + обработка с ровным шагом (`core/ingest.py`).
- **Метрики качества:** event precision / recall, F2 для критичных и F0.5 для предупреждений,
  ложные тревоги в час на камеру, оповещений на инцидент (цель 1,0), время до тревоги p50/p95.
- **Производительность на LinQ:** загрузка TPU (busy / wall), FPS на поток, задержки моделей,
  сколько камер выдержит узел — на вкладке «Система».
- **Квантование и компиляция:** ONNX (статический вход, batch 1, без NMS в графе) отдаём организаторам или
  компилируем сами SDK в Docker с калибровкой на своих кадрах: `core/tools/make_calib.py` → `core/tools/compile_tpu.py`
  (команды — в `core/README.md`, раздел «Своя компиляция»).

## Открытые вопросы к экспертам

  задаче (заголовок `uri`), так что чередовать можно — вопрос, сколько стоит переключение (замерить).
- ~~Можно ли вызывать инференс из нашего бэкенда?~~ Да: облако принимает задачи через RabbitMQ `10.0.114.30:5672`
  (`bench/linq_cloud.py`), с ноутбука — если VPN пускает маршрут до брокера; иначе конвейер запускается в Jupyter.
- Отдаёт ли API LinQ собственную загрузку ускорителя? Загрузку — нет, но воркер присылает `inference_time` каждой задачи,
