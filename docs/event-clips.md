# Видеоклипы и проверка событий оператором

Обработчик создаёт событие сразу после срабатывания правила. Фото отправляется сразу,
клип появляется в той же записи после сбора следующих секунд и кодирования.
Статус оператора при поступлении клипа или уточнения события сохраняется.

## Запуск

Из корня репозитория установите зависимости в своё виртуальное окружение:

```sh
python -m pip install -r core/requirements.txt -r journal/requirements.txt
```

В первом терминале запустите сервер (SQLite для локального запуска):

```sh
cd journal
DEMO_MODE=0 python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте http://127.0.0.1:8000/ui/. Сервер отдаёт и сайт, и API, и медиа;
отдельно запускать HTML-файл не нужно. Для PostgreSQL можно использовать существующий
`journal/docker-compose.yml` и инструкции `journal/README.md`.

Во втором терминале из корня проекта запустите обработку с настроенными моделями,
камерой и зонами в `core/cameras.yaml`:

```sh
python -m core.run --config core/cameras.yaml --journal http://127.0.0.1:8000
```

Для проверки файла можно добавить `--source /полный/путь/video.mp4 --offline`.
Экспорт моделей описан в `core/README.md`. Буферизация работает и с CPU, и с LinQ:
она не зависит от выбранного способа инференса.

## Буфер и окна записи

Карточка сценария задаёт `evidence.clip_sec: [-10, 5]`: 10 секунд до подтверждающего
кадра и 5 после него. Отсчёт идёт от времени исходного кадра, а не времени ответа
модели. В режиме камеры кадры сохраняет поток захвата, даже когда модель занята.
В режиме `--offline` буфер получает кадры последовательной обработки файла.

В `core/cameras.yaml` секция `clips` задаёт частоту записи (10 FPS), ширину (до 960),
историю (30 секунд), предел JPEG-истории (64 МиБ), кадров одного события (32 МиБ)
и число незавершённых клипов (8 на камеру). Настройки можно переопределить в камере.
Это лимиты сжатых кадров, а не всей памяти процесса. История должна покрывать
время до события плюс задержку инференса. При превышении памяти старые кадры удаляются.

Кодирование H.264 MP4 выполняется в фоне через FFmpeg из `imageio-ffmpeg`.
Клипы без звука. При разрывах захвата предыдущий кадр повторяется, сохраняя временной
масштаб. При завершении видео сохраняется доступная часть; неполный клип помечается
в интерфейсе. Переполнение очереди или ошибка кодирования отображается в событии.
При штатной остановке программа дожидается кодирования и очереди отправки.

## Интерфейс и API

Оператор открывает событие, смотрит фото и видео, вводит имя и комментарий, выбирает
«Подтвердить», «Ложное срабатывание», «Передать мастеру» или «Закрыть».
Сервер сохраняет статус и историю: кто, когда и с каким комментарием изменил запись.

- `POST /api/events/{id}/media?kind=clip` прикрепляет видео.
- `PATCH /api/events/{id}` с `{"extra": {...}}` дополняет сведения обработчика,
  включая уточнение падения и состояние клипа; изменение статуса здесь запрещено.
- `POST /api/events/{id}/status` сохраняет решение оператора с историей.
- `/ws/events` уведомляет сайт о новых событиях, решениях и появлении медиа.

Страница обновляет открытую карточку, сохраняя введённый комментарий. После восстановления
WebSocket она перечитывает данные сервера. Время истории возвращается с часовым поясом UTC.

Локальные фото и клипы остаются в каталоге evidence обработчика. Существующая очередь
отправки имеет ограниченные повторы; постоянной очереди с восстановлением после перезапуска
пока нет. Если сервер долго недоступен, потребуется повторная отправка локального файла.
Авторизация операторов не добавлена: имя вводится вручную, как в исходном журнале.

## Проверка

```sh
python -m pytest core/tests -q
cd journal
python -m pytest -q
```

Проверки покрывают задержанный инференс, перекрывающиеся события, конец видео, лимиты,
ошибку кодирования, воспроизводимый H.264, загрузку и частичное чтение медиа, уведомления
WebSocket и сохранение решения оператора при последующем обновлении события.
